## PR 3 — sdk-feedback 0037 (header creds + per-request path) — DOCS, then bump + publish

**Part A already shipped in 0.35.0.** The item was filed against 0.34.0; `headers` and
`secret_headers` exist today on both `call_external` (`api.py:1289-1290`) and
`deliver_to_external` (`api.py:1188-1189`). Verified against its criteria:

- "missing secret key fails naming the key" — tested: `integration-call.test.ts:506`
  (`404s (naming the key) when a secretHeaders secret is unset`), error text from
  `MissingHeaderSecretError` in `lib/outbound-headers.ts:60`.
- "AUTH_MODE=none sends no Authorization" — tested: `integration-call.test.ts:298`.
- "dry-run capture redacts values" — holds **by construction**: `secret_headers` values are secret
  KEY NAMES resolved server-side, so the real value never enters the SDK or a capture record. Say
  this in the PR body rather than adding a redaction mechanism for a value that is never present.

**Part B resolves as docs, not code.** `deliver_to_external` unconditionally sends
`Authorization: Bearer <SEND_API_KEY>` and 404s when that secret is unset
(`apps/api/src/handlers/integration-delivery.ts:~165-178`). So adding a `path` kwarg would still
not let the motivating partner (Weichert: no bearer + two credential headers) deliver. The only
coherent code version is path _plus_ optional auth — which re-creates `call_external` with
`method="POST"`. `call_external` already satisfies every criterion. The item explicitly blesses
this: "if the answer is instead 'use call_external for anything non-trivial', that is fine — but
then say so in the docs."

**Do:**

- `deliver_to_external` docstring — it is one fixed POST to a static `SEND_URL` with a bearer;
  point per-request-path / non-bearer / multi-header-credential cases at `call_external`.
- SDK README — same steer where delivery is documented as _the_ way to send a mapped body.
- The MCP delivery prose (`cli/mcp_server.py`) — same.
- Record the answer to the item's open question: the intended shape for a two-header credential is
  caller-specified `secret_headers` (shipped 0.35.0), **not** a new
  `AUTH_MODE=client_id_secret_headers`.
- **CHANGELOG + version bump here only.** `0.36.1` if this stays docs-only; `0.37.0` if any code
  lands. Then `/workstream-finish`, and after it merges tag the **merge commit on synced main**:
  `git tag -a sdk-python-v<ver> -m "…" <merge-sha> && git push origin sdk-python-v<ver>`
  → `release-sdk-python.yml` publishes via trusted publishing. Verify on PyPI itself, not just a
  green workflow: `curl -s https://pypi.org/pypi/pegasus-workflows-sdk/json | python3 -c "import json,sys; print(json.load(sys.stdin)['info']['version'])"`.
  Tagging the branch instead of the merge commit points PyPI at a commit that never becomes main.
