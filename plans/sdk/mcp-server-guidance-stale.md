# SDK spec — MCP server guidance drifted from 0.6.0 behavior (`from_runtime` + mandatory `workflow.mmd`)

- **Origin:** pegasus-workflows repo (`~/repos/pegasus-workflows`), `sdk-feedback/0011-mcp-server-stale-after-0.6.0.md`
- **Status:** Proposed
- **Filed:** 2026-06-30
- **SDK version when filed:** 0.6.0
- **Area:** tooling (MCP) / docs / CLI (`package`)

## Problem

The bundled MCP server (`pegasus-workflows mcp`) is the **provider-agnostic
authoring context** for any AI coding agent that isn't Claude Code (the stated
goal of the AI-authoring-MCP-server spec / `CLAUDE.md` → "AI tooling for SDK
developers"). After 0.6.0 two pieces of it no longer match real SDK behavior:

1. **`from_runtime()` is not taught — the guide still shows the pattern the
   runtime-env-var spec killed.** `resource_guide_authoring` (`cli/mcp_server.py`)
   renders an Activities example that constructs the client the old way:

   ```python
   @activity.defn
   async def fetch_quote(quote_id: str) -> dict:
       client = PegasusClient(base_url="https://...", token="vnd_...")
       ...
   ```

   `grep -n from_runtime cli/mcp_server.py` returns nothing. 0.6.0 shipped
   `PegasusClient.from_runtime()` and the **SDK README** was updated to recommend
   it (validated under the runtime-env-var spec), but the **MCP authoring guide
   was not** — so an agent reading the guide is steered back toward hardcoded
   construction (literal `base_url`/`token`), i.e. the runtime-failing shape that
   spec exists to prevent.

   _Mitigation that already exists:_ `pegasus://reference/api` is generated by
   introspecting `PegasusClient` (`inspect.getmembers`, `mcp_server.py:311`), so
   it already lists `from_runtime` with its docstring. The drift is that the
   **teaching guide contradicts the reference**.

2. **The new mandatory `workflow.mmd` packaging gate is undocumented in MCP and
   cannot be satisfied through MCP.** As of 0.6.0 `package` hard-fails when a
   workflow lacks `<source_dir>/workflow.mmd`:

   ```
   manifest error: workflow send_order_saved_sms: send_order_saved_sms/workflow.mmd
   not found — run `pegasus-workflows diagram` to generate the workflow diagram first
   ```

   `tool_package_project` wraps the same `package_project`, so an MCP agent gets
   `{"ok": false, "error": "...workflow.mmd not found..."}`. But:
   - no MCP **resource** (authoring guide, manifest reference) mentions the
     requirement; `grep -niE "diagram|mmd|mermaid" cli/mcp_server.py` is empty;
   - no MCP **tool** can produce the diagram — the `diagram` CLI subcommand is
     LLM-backed and is not exposed as an MCP tool.

   So a non-Claude agent that scaffolds → edits → packages entirely through MCP
   hits a dead end it cannot resolve without dropping to a shell command the
   server never told it about.

## Why it matters

MCP is the entire "any capable AI agent can author Pegasus workflows" story (the
AI-authoring-MCP-server spec). When its guidance drifts, the cost lands precisely
on the audience it exists for — non-Claude-Code agents, which have no `CLAUDE.md`
to fall back on. Today such an agent is (1) taught the hardcoded client pattern
that fails at runtime, and (2) blocked at `package` with no in-MCP way forward.
Claude Code users are insulated (the pegasus-workflows `CLAUDE.md` carries the
correct guidance), which is exactly why the drift is easy to miss until an
external agent hits it.

## Proposed change

1. **Sync the authoring guide to the README.** Update `resource_guide_authoring`'s
   Activities example to build the client with `PegasusClient.from_runtime()` and
   note the runtime env-var contract. Better: generate the guide and the README
   from one source so they can't diverge again.
2. **Document the diagram requirement** in `resource_guide_authoring` and
   `pegasus://reference/manifest` (packaging requires `<source_dir>/workflow.mmd`).
3. **Close the MCP packaging dead-end** — pick one:
   - expose a `generate_diagram` MCP tool; or
   - have `package` auto-generate a placeholder `workflow.mmd` when missing; or
   - downgrade the missing-diagram from a hard error to a warning.
     At minimum, `tool_package_project`'s error must name a remedy reachable from
     within MCP.

Backward-compatible: all changes are to served text / tool surface, not to the
authoring API.

## Acceptance criteria

- [ ] The served `pegasus://guide/authoring` Activities example constructs the
      client via `PegasusClient.from_runtime()` — `grep "PegasusClient(base_url="`
      over the served guide returns nothing and `grep "from_runtime"` returns a
      hit — and it references the `PEGASUS_API_BASE_URL` / `PEGASUS_RUNTIME_TOKEN`
      runtime contract.
- [ ] `pegasus://guide/authoring` and/or `pegasus://reference/manifest` state
      that packaging requires `<source_dir>/workflow.mmd`.
- [ ] An MCP-only flow gets from a freshly scaffolded project to a packaged zip
      using MCP tools alone (no shell `pegasus-workflows diagram`): either a
      `generate_diagram` tool exists, or `tool_package_project` no longer hard-
      fails on a missing diagram. Verified by running that flow end to end.
- [ ] If the diagram stays a hard gate, `tool_package_project`'s error string
      names the in-MCP remedy.
