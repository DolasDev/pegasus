## Contradictions — the real design decisions

### 1. What a shipment is, and whether one order can carry more than one

- src:pegii-order says one Sale = one shipment by construction — the Weichert mapping wraps the order root into a one-element array with `$each`, and the workflow relies on it ('a pegII order produces exactly one shipment whose supplierShipmentId is the pegII order id'). Nothing in the evidence shows a shipment as a distinct entity inside a Sale, and its own open question 11 asks whether a Sale can ever be more than one shipment.
- src:pegasus-integration-floors says an order CONTAINS shipments — `DemoPartnerOrderSchema` holds `shipments: z.array(...)` and the milestone facts count shipments-with-pack-load-actuals, which is meaningless at arity one.
- src:sirva-ade says one registration IS the shipment, and a split MINTS A NEW VALUE OF THE SAME IDENTIFIER: CamisRegNumber = shipment(6) + overflowSeq(2) + transferSeq(2), with segments independently addressable via TransferNumber/OverflowNumber/MassMoveNumber.
- src:alvys-api says the commercial shipment (Load) and the execution (Trip) are separate entities with the seam stated as invariants — stops belong to the trip, the load's origin/destination are DERIVED from them, and a load with no trip returns 404.
- src:pegasus-cloud-domain says none of the above — `Move` fuses order + shipment + route into one aggregate with one origin and one destination, and its own analysis says adopting it 'forecloses consolidation, multi-shipment trips, split deliveries, partial loads, and SIT-then-deliver — every one of which is normal HHG'.
- src:uncefact-mmt-rdm says a single Trade Item CANNOT be split across Shipments (BRS p.15) while src:uncefact-scrdm says it CAN (BRS p.16) and the parent Buy-Ship-Pay BRS says it 'is related to one shipment' (p.15) — three UN/CEFACT documents in one download, three rules.

**Why it matters.** This is the A2/A3 boundary and it decides whether the model can ever represent a vehicle shipment or a separate storage shipment on one booked order. It is also the thing our own two systems answer differently from each other AND from the partner contract we already publish: pegII says one, the live Weichert floor says many. Whatever phase 3 picks, one of those two is wrong today and someone is mapping around it.

### 2. Does a stop belong to a trip or to a shipment

- src:pegii-longhaul says neither owns the other — a trip owns activities, never shipments, and shipments attach to a trip ONLY through their activities; `TripService.getTrip` reconstructs trip.shipments from the distinct order_num of its activities. This is the only internal model where trip != shipment.
- src:open-trip-model says the trip owns ordered Stop actions and consolidation needs no concept at all: N shipments on one trip is N load actions at N stops referencing N consignments, the default reading rather than a special case.
- src:omnitracs-roadnet, src:samsara, src:gtfs and src:atlas-world-group-api all say stops belong to the route/trip — Atlas's Stop carries ord_hdrnumber AND lgh_number AND mov_number AND mfh_number independently.
- src:pegasus-cloud-domain and src:pegasus-cloud-prisma say the stop belongs to the SHIPMENT — `Stop.moveId` is mandatory — which makes consolidation structurally inexpressible; and the `stops` table has no write path at all, so it is a dead column today.
- src:project44 says the shipment owns its stops and there is no trip entity; the vehicle is reachable only as 'the id of a route segment [which] can be used to associate the event with a specific vehicle'. Its `Load` DIVIDES a multi-stop shipment into A→B pieces and never joins two.
- src:atlas-world-group-api contradicts ITSELF: `shipment-management-v1` nests `trips[]` inside `Shipment`, which its own analysis says 'inverts the real relation' and is an artefact of serving the trip filtered to one order.

**Why it matters.** Consolidation is the normal case for a van-line agent and it is the single capability that stop-ownership decides. Two of the three sources closest to our own architecture (Cloud, project44) foreclose it, and Cloud is the system we are building. If the reference model puts stops on the shipment, Cloud is validated and consolidation is permanently unrepresentable; if it puts them on the trip, Cloud needs a new aggregate.

### 3. Where the planned / estimated / actual distinction lives

- src:project44, src:atlas-world-group-api, src:samsara and src:pegii-longhaul say NAMED FIELDS — p44 has plannedDateTime / estimateDateTime / dateTime plus initialPlanned vs latestPlanned split by asserter; Atlas has five kinds on one stop (scheduled / agreed / ETA-ETD / actual / CONFIRMED); Samsara has four families (scheduled / appointment window / eta / actual) plus an on-time tolerance.
- src:dcsa says ONE FIELD PLUS A CLASSIFIER — a single `eventDateTime` with `eventClassifierCode` ACT|PLN|EST|REQ, constrained per event type (document status is always ACT), so the same event type is republished as the answer firms up.
- src:open-trip-model says A LIFECYCLE DIMENSION ON THE RECORD — the same stop published five times at requested / planned / projected / actual / realized, with `result` legal only on actual/realized, and the differences between readings ARE the plan-vs-execution record.
- src:gtfs says DEVIATION FROM A PUBLISHED PLAN — StopTimeUpdate carries delay and/or time plus `uncertainty`, where uncertainty 0 means observed, and `timepoint` marks confidence on the PLAN itself.
- src:stedi-x12-reference says IN THE STATUS CODE — `AG Estimated Delivery` and `X1 Arrived at Delivery Location` are two of 42 codes in one flat list, so a new temporal reading is a code addition.
- src:uncefact-scrdm says ON THE ASSOCIATION NAME — Planned_Delivery.SupplyChainEvent vs Actual_Delivery.SupplyChainEvent are two instances of a simple event class, with superseded values KEPT as Previous_Delivery; while src:uncefact-mmt-rdm, in the same 245 MB download, says the opposite: one event object carrying EstimatedOccurrenceDateTime / ActualOccurrenceDateTime / ScheduledOccurrenceDateTime / RequestedOccurrenceDateTime simultaneously, revised in place.

**Why it matters.** Six mutually exclusive answers, one of them self-contradictory inside a single publisher's package. It is irreversible once the catalog publishes, it decides whether the catalog is append-only or revisable, and the pegII constraint may settle it for us: if pegII overwrites one field on a form save (which form-and-save CRUD usually does) then we can publish ACT but can never reconstruct EST history, and OTM/SCRDM's 'keep both readings' shape buys nothing on the legacy side. That check has not been run.

### 4. What storage-in-transit IS, structurally

- src:stedi-x12-reference says a SHIPMENT STATUS — `BC Storage in Transit`, one code in a flat list of 42, with no duration, no in/out pair, no warehouse party. Its own analysis calls it 'an interop token, not a model' and warns that using it as the model 'would be the A5 disaster'.
- src:atlas-world-group-api says a RECORD HUNG OFF A STOP — with sit_date / siT_Out_Date, days_authorized, a `permanent` boolean, named causes as discrete flags (market_Saturated, warehouse_full, long_Cartage_Denied, carrier_Convenience), and `sit_xdl_stop_number` naming the cross-dock delivery-out stop in the stop sequence.
- src:milmove-mymove says A SET OF SERVICE ITEMS GROUPED PER STAY — `SITServiceItemGrouping` groups by the date they went into SIT, so one shipment can have several distinct stays; the day allowance is POOLED across origin and destination on the shipment, and extension is a request lifecycle with seven reason codes.
- src:weichert-supplier-api says FOUR DATE PAIRS ON THE SHIPMENT (in/out x origin/destination) plus a `directOrSIT` routing decision — and permanent storage is A DIFFERENT PRODUCT: LTS has its own order type, its own endpoints, its own date pair (ltsInDate/ltsOutDate, note 'scheduled' not 'estimated'), its own cost structure and a back-reference to the HHG request it came from.
- src:dp3-400ng says AN INTERVAL SEQUENCE WITH ITS OWN ARITHMETIC — SIT start is a derived date (= the TSP's first available delivery date, and the arrival date must NOT be entered as the SIT entry date), both entry and removal days count, re-entry restarts a first-day charge, accrual stops at the 5th government business day after the requested delivery date even if the goods are still there, and termination at midnight makes the warehouse the final destination under that BL with the original BL unrevivable.
- src:cfr-49-375 says THREE DIFFERENT SITUATIONS that most models conflate — shipper-requested SIT (tariff-bounded, carrier liability continues), carrier-account storage under §375.607 (carrier elects because it can tender >24h early and the shipper will not accept; carrier's expense, carrier's liability), and permanent storage after a dated conversion. They differ in payer, cause and who elects.
- src:smartmoving-api says A BILLING ACCOUNT — a storage account per customer with accountNumber, PrePay/PostPay, a valuation method and a next-invoice date, where the physical movements are separate JOBS (StorageInBound / StorageOutBound) — and the account has no in or out date at all.
- src:sirva-ade says A RECORD WITH NO IDENTITY — InDate and OutDate arrive TOGETHER at AddSIT time, so planned and actual are indistinguishable, and ChangeSIT/DeleteSIT cannot say WHICH SIT they refer to on a shipment with both origin and destination storage.
- src:pegasus-cloud-domain says A STOP TYPE — `StopType.STORAGE`, an enum value that no code in the estate reads, which its own analysis calls 'a trap, not a head start' because storage-as-a-point-you-pass-through has no duration, no warehouse party, no in/out pair and no permanent boundary.

**Why it matters.** Seven incompatible shapes for the area our tenants actually live in, and the disagreement is not cosmetic — status vs stop vs interval vs account decides whether SIT duration, the delivery-out leg, re-entry and the storage agent are representable at all. Worse, our two systems are at the two weakest ends: Cloud has the enum-value trap, and pegII's `WarehouseSummary` has never been opened. Pick the shape before anyone maps anything.

### 5. Where the permanent-storage boundary sits

- src:weichert-supplier-api says it is A SEPARATE PRODUCT — LTS is its own order type with its own endpoints, dates, costs and a back-reference to the originating HHG request. Its analysis argues this is 'a cleaner answer than a duration threshold on SIT'.
- src:smartmoving-api says it is AN ENUM ON THE ACCOUNT — `StorageType = SIT | Permanent`.
- src:atlas-world-group-api says it is A BOOLEAN ON THE SIT RECORD — `permanent`.
- src:cfr-49-375 says it is A DATED, NOTIFIED EVENT THAT SHIFTS LIABILITY — conversion ends carrier liability, subjects the goods to the warehouseman's rules, opens a 9-month claims window, and requires the goods to be placed IN THE SHIPPER'S NAME; and if the notice was never given, liability runs to the end of the day AFTER notice was actually given (a computed instant that depends on evidence of an act).
- src:dp3-400ng says the same shape far more precisely — liability terminates at midnight of the day named in the DPS notice, the warehouse BECOMES the final destination under that BL, the original BL cannot be revived or reinstated, and the customer replaces the Government as the depositor.
- src:sirva-ade says it is A CHARGE CODE — `NTSP` NON-TEMP STORAGE CHARGE, and nothing else.

**Why it matters.** A flag, a separate product and a liability-shifting event are three different models with three different consequences for claims, billing and who holds the goods. The regulatory sources (which bind us) treat it as an event; the vendor sources treat it as an attribute. If the model picks the attribute, the 9-month claims window and the change of depositor have nowhere to live.

### 6. What 'delivered' means

- src:cfr-49-375 says it is THREE DISTINCT ACTS — tender for delivery (§375.603), relinquish possession on payment of the lawful maximum (§375.407), and delivery receipt (§375.701) — and that 'at destination, tendered, payment not made, possession retained' is a lawful and common state that a model with a single `delivered` cannot represent.
- src:gs1-epcis-cbv says arriving != receiving != accepting, defined and MUTUALLY EXCLUSIVE, with `arriving`'s own example spelling out 'Shipment has not yet been received or accepted', and `accepting` meaning a change of possession and/or ownership.
- src:stedi-x12-reference says it is six codes — AJ Tendered for Delivery, AV Available for Delivery, AH Attempted Delivery, AP Delivery Not Completed, X1 Arrived at Delivery Location, D1 Completed Unloading at Delivery Location — plus X5 (at the dock) distinct from X1 (at the site).
- src:pegasus-integration-floors and src:weichert-supplier-api say it is INFERRED FROM A DATE FIELD — 'Delivered' is derived from the presence of deliveryDate1.actual; there is no event, no asserter, no observation time.
- src:pegii-order says it is A FREE STRING — `Survey.SerivceStatus = 'Delivered'` — which is CURRENT STATE, not an asserted transition; our own overlay had to delete an authority rule because enforcing it rejected orders that merely SAT in a status.
- src:sirva-ade says it is an event whose DateTime is the RECORDING time, not the occurrence time ('the system is updated to reflect the driver has loaded'), with no separate occurred-at anywhere.
- src:dcsa says the shipment has no lifecycle at all — only DOCUMENTS have status; 'what state is my shipment in' is answered by replaying the event stream.

**Why it matters.** This is the fact every partner integration, every customer notification and every claim clock hangs off, and the corpus gives at least four incompatible readings. The regulatory reading (three acts) is binding on us and is the one no vendor source supports. Our own live Weichert config already infers it from a date field, which means the gap is in production, not hypothetical.

### 7. Who asserts a fact, and whether two parties may disagree about the same one

- src:dcsa says EVERY EVENT NAMES ITS PUBLISHER AND THE ROLE IT PLAYED — `publisher` + `publisherRole` (CA carrier / AG carrier's local agent / VSP visibility service provider / SVP other), made MANDATORY in event domain 3.1.0.
- src:gs1-epcis-cbv says the opposite by omission — there is no per-event publisher; sender/receiver live on the enclosing document, so provenance is per-batch and is LOST the moment events are re-hosted by a repository. Its own analysis calls this its biggest gap.
- src:omnitracs-roadnet says provenance is a value-object on the measurement — `DataSource` with nine values including `DispatcherEntered` (a human typed it), `GeoComputed` (a geofence did), `IgnitionComputed`/`OdometerComputed` (a sensor inferred it) and `AssumedFromProjection` (nobody did — we kept the plan and nothing contradicted it).
- src:samsara says `source: automatic | driver | admin` on every route update — with `automatic` as an explicit ASSERTION rather than an absence — plus a 15-value `assignmentType` recording how the driver-vehicle binding itself was asserted (static vs faceId vs qrCode vs RFID).
- src:project44 says a time value is an ASSERTION not a number — `dateTimes[]` carries type + source + sourceIdentifiers (device/vehicle/carrier) + sequence + lastModified + `selected`, publishing the winner alongside the losing candidates so the resolution rule is auditable.
- src:milmove-mymove says THREE ASSERTION CLASSES for the same real event — the customer's requested date, the mover's actual date, and a government inspector's `observed*` dates on an evaluation report, coexisting without contradicting the schema.
- src:gtfs says the question is structurally unaskable — one publisher by construction, no actor on any StopTimeUpdate.
- src:sirva-ade and src:x12-858-implementation-guide both say the DIRECTION OF TRANSMISSION is the entire authority model — no element records who keyed it.

**Why it matters.** This is the user's stated situation made concrete: the driver's Omnitracs or Samsara feed, the hauling agent and the destination agent will all assert the same arrival, sometimes inconsistently, and a shipper's visibility platform will later assert a fourth. Whether the model can hold competing assertions — and whether it records that a value was ASSUMED rather than observed — has to be decided at v1, because per-event publisher identity cannot be retrofitted once partners are parsing the envelope.

### 8. How a wrong fact is corrected

- src:gs1-epcis-cbv says APPEND-ONLY WITH TWO DISTINCT REASONS — `errorDeclaration` carries declarationTime (separate from the preserved eventTime) and one of `did_not_occur` (a pure retraction, which SHALL NOT carry corrective event ids) or `incorrect_data` (a supersession with the replacement explicitly linked); and corrections are queryable as a class.
- src:dcsa says ONE BLUNT MECHANISM — `retractedEventID` in metadata with the payload omitted, no reason, no corrective link, no separate declaration time. Its own analysis says this is strictly weaker and 'do not copy it'.
- src:x12-858-implementation-guide says TWO NAMED OPERATIONS WITH DEFINED EFFECTS — BX01 `01` means 'the previous status should be disregarded and THE PRIOR STATUS should be considered the current status' (retract-to-previous), `03` means remove the record entirely; and a retraction carries the FULL ORIGINAL CONTEXT so the receiver can identify what is being undone.
- src:stedi-x12-reference says the 214 HAS NO CORRECTION AT ALL — there is no purpose code on a status message, so a wrong status can only be superseded by a later one with a later timestamp. Its analysis calls this 'the single biggest gap in the standard for a system of record'.
- src:alvys-api says it depends on the KIND of fact — `DELETE /trips/{id}/stops/{id}/arrival` is a published un-do for an operational fact ('effectively marking the stop as not yet arrived'), while for money 'a correction is a new record, not a retry' and a settled record returns 409 'do not retry, post a correction instead'.
- src:samsara says corrections are FIRST-CLASS OPERATIONS with diffs — `stop arrival time updated` and `stop completion time updated` are distinct from `stop arrived`, delivered with a before/after diff on an immutable append-only feed.
- src:gtfs says the next snapshot IS the correction — `FULL_DATASET` overwrites all preceding realtime information, with no retraction, no supersedes link and no history.
- src:cfr-49-375 and src:dp3-400ng say corrections are APPEND-ONLY SIGNED DOCUMENTS — a new signed estimate, a written attachment to the BOL, notations added to the inventory at delivery with a copy to the shipper; and under DP3 the carrier may not alter the BL at all, only the Government may, and only through a named instrument (SF1200).
- src:pegii-longhaul says corrections are DESTRUCTIVE OVERWRITES — an edited actual_date replaces the old value, a removed activity is DELETEd not tombstoned, and last-writer-wins over a stale page is recorded as intended behaviour rather than a defect.

**Why it matters.** A published event cannot be unpublished, so this is the one decision that has no migration path. Four distinct ideas are in play and they are not alternatives: retract-vs-supersede (EPCIS), retract-to-previous-vs-expunge (X12 858), correct-the-fact-vs-post-an-offsetting-record (Alvys, SIRVA's AdjCode), and who-is-authorised-to-amend (CFR/DP3). Our own systems currently do the worst available thing.

### 9. Open vocabularies versus closed enums

- src:gs1-epcis-cbv says OPEN BY NAMESPACE — every vocabulary field is `anyOf [ your-own-URI, CBV enum ]`, so a tenant mints `https://pegasus.example/cbv/bizstep/sit_in` and it validates; extension is by URI namespace rather than by an `OTHER` escape hatch that destroys filterability.
- src:dcsa says CLOSED, WITH PROCESS INSTEAD — every enum is closed, there is no additionalProperties and no vendor field; adding a value is a versioned release of the shared domain plus a release of every dependent API, and the changelogs show the cost ('added new enum values to shipmentEventTypeCode - PENC, CANC' is a release event). The payoff is that a consumer can exhaustively switch on a code.
- src:omnitracs-roadnet says CLOSED AND CONFIG-GATED — custom properties exist but must be pre-declared in the desktop client or 'they will not be able to be posted or retrieved', i.e. a field that silently drops on write.
- src:samsara says CLOSED WITH A CATCH-ALL — `unspecified` and `unknown` are declared enum members precisely so new kinds do not break a consumer's parser, plus versioned webhooks and declared maturity labels.
- src:dp3-400ng says CLOSED WITH A MANDATORY-JUSTIFICATION ESCAPE HATCH — item code 226A exists for 'any authorized charge that does not have a designated service code' and REQUIRES a narrative note.

**Why it matters.** Both the EPCIS and DCSA analyses independently name this as the single biggest C8 decision in the catalog, and both say it must be made once for the whole vocabulary rather than per field. It determines whether a tenant can add a status without a release, and whether a consumer can write an exhaustive switch — and those are not both achievable.

### 10. Who the 'shipper' is

- src:cfr-49-375 says the INDIVIDUAL SHIPPER is a four-part conjunctive test — named as shipper/consignor/consignee on the face of the BOL, AND owns the goods, AND pays his or her own tariff charges — and carves out commercial shipper and government-bill-of-lading shipper against it.
- src:dp3-400ng inverts it — 'In DPS, the shipper is typically the Government, except for Self-Procured moves', and the service member whose goods are moving is the CUSTOMER / OWNER.
- src:project44 says `Party.partyType` is 'the relationship THE SHIPPER has to the party' — the whole model is written from the shipper's chair, and its `BOOKING_AGENT` is an ocean booking office, not a van-line booking agent.
- src:milmove-mymove uses both key words wrongly for us — `Order` is the service member's PCS orders (the AUTHORITY to move, not an order for service) and `MTOAgent` is a PERSON who hands over or receives goods, not a company in a van line's network.
- src:smartmoving-api collapses the distinction entirely — the customer is the payer and the transferee at once, and there is no account or RMC anywhere.
- src:weichert-supplier-api adds a fourth reading — the corporate client account pays, the transferee's goods move, Weichert is the RMC, and our tenant is the 'supplier'.

**Why it matters.** Four sources use the same word for four different parties, and two of them are the regulatory sources that bind us. The 400NG analysis draws the right conclusion: the model should probably avoid the bare word 'shipper' entirely and separate payer / account party from goods owner / transferee. This is a naming decision with teeth, because getting it wrong silently mis-maps every DoD and every corporate-relocation shipment.

### 11. Our own published rules cite evidence we do not hold

- src:weichert-supplier-api says SIX RULES IN OUR LIVE CONFIG CITE TEXT THAT DOES NOT EXIST — rules.json carries sourceRef strings beginning 'Weichert API:' quoting sentences such as 'Pack Date 1 Actual and Load Date 1 Actual are required on at least one related Shipment Order before Service Status can become In Progress'. Verified by grep across the full 3,578-line extraction of weichert-api.odt: no occurrence of 'required to submit', 'Pack Date 1', 'Estimated Total Cost', or ANY status-transition precondition. The document states exactly seven behavioural rules and none is a transition rule.
- src:weichert-supplier-api also says THOSE RULES CLOSE THE SET ON A NORMAL MOVE — evaluated directly, `pre-in-progress-forbids-pack-actual` and `in-progress-requires-load-actual` together leave NO valid service status for a shipment that is packed but not yet loaded. Every status describing work in progress is rejected; only Declined, Cancelled and the undocumented `Authorized` pass. The corpus pins both halves independently without either case noticing.
- src:pegii-order says OUR STATUS VOCABULARY IS OUR GUESS — `mapStatus` collapses a free-form pegII string onto booked|in_progress|completed and DEFAULTS EVERY UNRECOGNISED VALUE TO `booked`, so an unknown pegII status is indistinguishable from a booked order; the synonym table is ours, not pegII's, and is unverified.
- src:pegasus-integration-floors says THE CANONICAL SHAPE IS A FICTIONAL PARTNER'S — the nine-value serviceStatus enum every partner on that floor inherits originated in 'a fictional example supplier integration', and it fuses three lifecycles in one string (Requested/Awarded/Declined are award states, Accepted/Submitted are estimate states, In Progress/Delivered/Completed are execution states).

**Why it matters.** This is not a source-comparison problem, it is an integrity problem in material the comparison will treat as evidence. Six production rules attribute themselves to a vendor document that does not contain them (most plausibly they are Supplier Portal UI validation messages — a legitimate but DIFFERENT source that has no registry entry). Until that is resolved, any phase-3 claim of the form 'Weichert requires X' is unsupported, and the packed-but-not-loaded gap is a live defect in a GLOBAL-published config.

## Recommended order for phase 3

1. Write the A3 comparison FIRST, before A1.
